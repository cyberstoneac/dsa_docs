# Reflection & Classloaders

> **JDK context:** Reflection has been part of Java since 1.1. `MethodHandles`
> and `invokedynamic` (Java 7) provide a faster alternative. `VarHandle`
> (Java 9) modernizes low-level access. `MethodHandles.Lookup` (Java 9+) uses
> module-aware access rules.

## Mental Model

**Reflection** lets Java code inspect and manipulate classes, methods, and
fields **at runtime** — even private ones. **Classloaders** are how the JVM
finds and loads those classes in the first place.

```d2
direction: right

source: "MyClass.java" {
  style.fill: "#e3f2fd"
}
compiled: "MyClass.class" {
  style.fill: "#fff9c4"
}

  style.fill: "#c8e6c9"

  style.fill: "#ffe0b2"
}

source.compiled -> compiled: "javac"
compiled.loaded -> loaded: "ClassLoader"
loaded.instance -> instance: "newInstance / ctor.newInstance"
```

**Interview line:** *"Reflection is the runtime type system — it lets you
work with classes you didn't know about at compile time. Classloaders are
how those classes get into the JVM in the first place."*

## Getting a `Class<?>` Object

Four ways:

```java
// 1. Class literal
Class<?> c1 = String.class;

// 2. From an instance
String s = "hello";
Class<?> c2 = s.getClass();

// 3. Class.forName (dynamic — the class name is a String)
Class<?> c3 = Class.forName("java.lang.String");

// 4. From a classloader
Class<?> c4 = ClassLoader.getSystemClassLoader().loadClass("java.lang.String");
```

**`Class.forName` vs `ClassLoader.loadClass`:**

| | `Class.forName` | `ClassLoader.loadClass` |
|---|---|---|
| Initializes the class | ✅ | ❌ |
| Runs static initializers | ✅ | ❌ |
| Returns | `Class<?>` | `Class<?>` |
| Typical use | JDBC driver loading, plugin discovery | Deferred loading |

`Class.forName("com.mysql.jdbc.Driver")` initializes the class, which
registers itself with `DriverManager` via a static block. That's why the old
JDBC pattern worked.

## Reflection — Inspecting Classes

```java
Class<?> clazz = String.class;

// Class metadata
clazz.getName();                 // "java.lang.String"
clazz.getSimpleName();           // "String"
clazz.getPackageName();          // "java.lang"
clazz.getModifiers();            // bitmask — check with Modifier.isFinal(...)
clazz.isInterface();             // false
clazz.isEnum();                  // false
clazz.isRecord();                // false (until Java 16+)

// Superclass and interfaces
Class<?> superclass = clazz.getSuperclass();       // Object
Class<?>[] interfaces = clazz.getInterfaces();      // [Serializable, Comparable, ...]

// Fields, methods, constructors
Field[] fields = clazz.getDeclaredFields();
Method[] methods = clazz.getDeclaredMethods();
Constructor<?>[] ctors = clazz.getDeclaredConstructors();
```

### `getDeclaredX` vs `getX`

| | `getDeclaredX` | `getX` |
|---|---|---|
| Scope | This class only | This class + inherited (public only) |
| Access | Public, protected, package, private | Public only |
| Use | Full inspection | Public interface |

## Reflection — Invoking Methods

```java
class Greeter {
    private String greet(String name) {
        return "Hello, " + name;
    }
}

Class<?> clazz = Greeter.class;
Object instance = clazz.getDeclaredConstructor().newInstance();

Method method = clazz.getDeclaredMethod("greet", String.class);
method.setAccessible(true);   // bypass private

Object result = method.invoke(instance, "Alice");
System.out.println(result);   // "Hello, Alice"
```

### Accessing private fields

```java
Field field = clazz.getDeclaredField("secret");
field.setAccessible(true);
Object value = field.get(instance);
field.set(instance, "new value");
```

### Performance

Reflection is **10–100× slower** than direct invocation. The JIT can't inline
reflective calls, and each call goes through access checks.

### Modern alternative — `MethodHandle` (Java 7+)

```java
MethodHandles.Lookup lookup = MethodHandles.lookup();
MethodType type = MethodType.methodType(String.class, String.class);
MethodHandle handle = lookup.findVirtual(Greeter.class, "greet", type);

Object result = handle.invoke(instance, "Alice");
```

`MethodHandle` is JIT-friendly and can be as fast as direct calls after warmup.
Modern frameworks use `MethodHandle` or generated bytecode instead of raw
`Method.invoke`.

## Common Uses of Reflection

| Use case | Example |
|---|---|
| **Frameworks** | Spring DI, Hibernate ORM, Jackson JSON |
| **Testing** | JUnit, Mockito |
| **Plugin systems** | Loading classes by name |
| **Serialization** | `ObjectInputStream` reads fields reflectively |
| **Annotations** | Process `@Override`, `@Autowired` |
| **JDBC drivers** | `Class.forName("com.mysql.Driver")` |
| **IDE tooling** | Autocomplete, debuggers |

### Example — DI container sketch

```java
// Register classes; container creates instances on demand
Class<?> clazz = Class.forName("com.example.UserService");
Constructor<?> ctor = clazz.getDeclaredConstructor(UserRepository.class);

// Instantiate with a dependency
UserRepository repo = new UserRepository();
Object service = ctor.newInstance(repo);
```

Frameworks like Spring do this at scale.

---

## Drawbacks of Reflection

- **Performance** — slower than direct calls
- **No compile-time safety** — errors surface at runtime
- **Breaks encapsulation** — private members become accessible
- **Harder to debug** — stack traces don't always show the reflection call
- **Modules (Java 9+)** — accessing JDK internals is restricted
- **Security** — reflective code can bypass security managers

**Rule:** use reflection only when you need runtime dynamism (frameworks,
plugins, generic infrastructure). Otherwise, prefer interfaces and generics.

## Classloaders — The Loading Mechanism

Every class is loaded by a `ClassLoader`. Java uses a **delegation hierarchy**.

```d2
direction: down

hierarchy: "ClassLoader Hierarchy" {
  style.fill: "#f5f5f5"

  bootstrap: "Bootstrap ClassLoader\n(loads java.base)\nnull reference" {
    style.fill: "#ffcdd2"
  }
  platform: "Platform ClassLoader\n(Java 9+, formerly Extension)" {
    style.fill: "#fff9c4"
  }
  app: "Application ClassLoader\n(Classpath)" {
    style.fill: "#c8e6c9"
  }
  custom: "Custom ClassLoaders\n(Plugins, app servers)" {
    style.fill: "#bbdefb"
  }
}
```

### Delegation model

When asked for a class:
1. First ask the parent classloader
2. Only if the parent fails, try to load the class yourself

This prevents user code from shadowing `java.lang.String`.

### Key methods

```java
protected Class<?> loadClass(String name, boolean resolve)
protected Class<?> findClass(String name)
protected Class<?> defineClass(String name, byte[] b, int off, int len)
```

- `loadClass` — the public entry point (delegation logic)
- `findClass` — where you fetch bytes (usually override this)
- `defineClass` — turn bytes into a `Class<?>` (cannot override)

### Custom classloader example

```java
public class MyClassLoader extends ClassLoader {
    private final Path root;

    public MyClassLoader(Path root) {
        super(MyClassLoader.class.getClassLoader());   // app loader as parent
        this.root = root;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        try {
            byte[] bytes = Files.readAllBytes(
                    root.resolve(name.replace('.', '/') + ".class"));
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
}
```

Use cases:
- **Plugin systems** — load plugins from external jars
- **Hot reload** — reload modified classes
- **Instrumentation** — modify bytecode before defining the class
- **Isolation** — Tomcat loads each webapp with its own classloader to avoid
  version conflicts

### The identity problem

Two classloaders loading the same `.class` bytes produce **two distinct
`Class<?>` objects**:

```java
Class<?> c1 = loader1.loadClass("com.example.Foo");
Class<?> c2 = loader2.loadClass("com.example.Foo");

System.out.println(c1 == c2);          // false
System.out.println(c1.equals(c2));      // false
```

**Consequences:**
- `instanceof` fails across classloaders
- Casts throw `ClassCastException`
- Static state is not shared
- `HashMap<Class<?>, ...>` treats them as different keys

This is a common source of "works on my machine" bugs in plugin systems and
app servers.

## `ClassNotFoundException` vs `NoClassDefFoundError`

| | `ClassNotFoundException` | `NoClassDefFoundError` |
|---|---|---|
| Type | Checked exception | `Error` |
| Thrown by | `Class.forName`, `ClassLoader.loadClass` | JVM during linkage |
| When | You explicitly ask for a class that doesn't exist | The JVM needs a class that was present at compile time but is missing or failed to load |
| Recoverable | ✅ (yes, you can catch it) | Usually no |
| Typical cause | Missing jar, typo in class name | Class absent at runtime, or its static initializer threw |

### Common `ClassNotFoundException` scenario

```java
try {
    Class<?> c = Class.forName("com.example.Foo");
} catch (ClassNotFoundException e) {
    // handle: load a fallback implementation, or log and continue
}
```

### Common `NoClassDefFoundError` scenario

```java
class Config {
    static {
        // throws during class initialization
        throw new RuntimeException("bad config");
    }
}

// First access → ExceptionInInitializerError
// Second access → NoClassDefFoundError (the class failed to initialize before)
```

The class was present, but its static initializer failed. Subsequent uses
give `NoClassDefFoundError` instead of the original cause.

### Other `NoClassDefFoundError` causes

- Missing jar on classpath at runtime (was there at compile time)
- Version mismatch — a dependency was removed in a later version
- Classloader isolation — the class is in a different classloader's scope

### Interview line

*"`ClassNotFoundException` is a checked exception you get when you ask for
a class that doesn't exist. `NoClassDefFoundError` is an Error you get when
the JVM needs a class that was available at compile time but isn't at runtime
— or whose static initializer failed."*

## Tricky Corners ⚠️

**`setAccessible(true)` is restricted by JPMS in Java 9+.** Accessing JDK
internals requires `--add-opens` or `--add-exports`. Reflective frameworks
often need these.

**`Class.forName` initializes the class** (runs static blocks). `loadClass`
doesn't.

**`getDeclaredMethods()` order is unspecified.** Don't depend on declaration
order.

**Reflection can break immutability.** `Field.setAccessible(true)` lets you
mutate `final` fields.

**Two classloaders, two classes.** `==`, `instanceof`, and casts fail across
loader boundaries.

**Classloader leaks** are the #1 cause of `OutOfMemoryError: Metaspace`.
Redeployed webapps can leak classloaders if threads or references retain them.

**`Class.getDeclaredConstructor()` requires the constructor to exist.** Use
`getDeclaredConstructors()[0]` if you don't know the signature.

**`newInstance()` is deprecated.** Use `getDeclaredConstructor().newInstance()`.

**Primitive classes are `int.class`, not `Integer.class`.** Different `Class<?>`
objects.

**Arrays have their own `Class<?>`:** `String[].class` is distinct from
`String.class`. `int[].class` ≠ `int.class`.

---

## Common Pitfalls

- Using reflection in hot paths — use `MethodHandle` or generate code.
- Assuming `Class.forName` and `loadClass` are interchangeable.
- Ignoring classloader isolation in plugin systems.
- Catching `NoClassDefFoundError` — usually a fundamental deployment problem.
- Not cleaning up classloaders on redeploy — Metaspace leak.

---

## Key Interview Tips

- Explain reflection's performance and safety trade-offs.
- Name the four ways to get a `Class<?>`.
- Draw the classloader hierarchy and delegation model.
- Explain "same class, two classloaders → different `Class<?>`."
- Distinguish `ClassNotFoundException` (checked exception) from
  `NoClassDefFoundError` (Error, often static-init failure).
- Mention `MethodHandle` as the modern, faster alternative.
